# dev-diagnose-repo

## 무엇을 하는가

코드 저장소(또는 그 일부)를 받아 **객관적 지표 7축의 한 페이지 진단 리포트** 를 만든다. 추측 없이 *측정 가능한 것만* 넣는다. 측정 못 한 축은 "측정 안 됨" 으로 명시.

## 언제 호출되나

- 새 repo 온보딩 시 "여기 위험 신호 어디?"
- 마이그레이션·현대화 *사전 평가*
- 보안 감사·성능 조사의 시작점
- 새 팀원에게 *코드 익히는 입구* 제공
- "이 코드 어디부터 손대지?" 가 막힐 때

## 언제 호출하지 않나

- 단일 함수·단일 파일 분석
- 진단 결과가 이미 손에 있는 상태
- 매우 작은 코드베이스 (단순 git log 만으로 충분)

## 7축

요약 — 측정 명령은 `references/axes.md`.

| 축 | 본다 |
|---|---|
| **Hotspot** | 가장 자주 바뀌는 파일 = 가장 자주 깨지는 파일 |
| **테스트 커버리지** | 안전망 없는 영역 |
| **결합도** | 변경 충격 반경 (순환 의존, fan-in) |
| **외부 통합** | DB · API · 큐 · 파일시스템 호출 지점 |
| **알려진 이슈 영역** | TODO · FIXME · HACK · hotfix 다발 |
| **빌드·배포 사이클** | 변경 → prod 까지 시간, 테스트 실행 시간 |
| **도메인 경계** | 응집도 높은 그룹 (bounded context 후보) |

## 작업 절차

1. **대상 범위 확정** — 전체 repo 인가, 특정 디렉토리/모듈만인가
2. **7축 *병렬* 측정** — 직렬로 한 번에 하나씩 가지 말 것. Bash/Read/Grep 으로 동시 시도
3. **측정 불가 축은 사용자에게 입력 요청** — 추측 채움 금지
4. **한 페이지 리포트로 정리** — 길이가 한 페이지 넘으면 너무 많은 디테일

## 출력 템플릿

```markdown
## 진단 — <대상>

- **변경 hotspot**: <상위 5~10 파일, 변경 횟수 포함>
- **테스트 커버리지**: <% 또는 영역별 부재 / 측정 안 됨 — 입력 필요>
- **결합도**: <순환 의존 / fan-in 높은 모듈>
- **외부 통합**: <DB·API·큐 위치 요약>
- **알려진 이슈 영역**: <TODO 집중 영역, hotfix 다발 파일>
- **빌드·배포 사이클**: <변경 → prod 시간, 풀 테스트 시간 / 측정 안 됨>
- **도메인 경계 후보**: <응집도 높은 그룹 2~5개>

### 위험 신호 요약
<2~3 문장 — 가장 두드러진 패턴>
```

## 안티 패턴

- ❌ 데이터 없이 *추측* 으로 축 채우기
- ❌ 7축 중 일부만 보고 리포트 출력 — 누락 축이 가장 위험할 수 있음
- ❌ 리포트가 한 페이지 넘어감 — 큐레이션 부족
- ❌ "이 코드 별로다" 같은 *비교 기준 없는* 평가
- ❌ Bash 측정 가능한 축인데 사용자에게 물음 — 직접 측정 우선
