# dev-plan-rollback

## 무엇을 하는가

prod 변경 계획을 받아 **"여기서 멈춘다"의 객관적 기준** 을 정의한다. 출력은 3~5개 신호, 각각:

1. 측정 가능한 임계값 (지표 + 값)
2. 대응 액션 (flag off · phase 보류 · 옛 구현 복원 등)
3. 에스컬레이션 경로 (누가 결정 · 어떻게 알림)

## 언제 호출되나

- 신규 배포 직전 ("뭘 보고 롤백 결정?")
- 마이그레이션·인프라 교체 계획
- 기능 출시 + feature flag 설계
- A/B 테스트 abort 기준 정의

## 언제 호출하지 않나

- 내부 리팩토링 (외부에 영향 없음)
- 테스트 코드 변경
- 이미 완료된 변경의 사후 분석 (post-mortem 영역)

## 좋은 신호 vs 나쁜 신호

| 좋은 신호 (측정 가능) | 나쁜 신호 (측정 불가) |
|---|---|
| 에러율 baseline +5% | "느낌이 안 좋다" |
| P95 응답시간 800ms 초과 | "테스트가 깨질 것 같다" |
| 같은 종류 incident 7일 안에 2건 | "팀이 불안해한다" |
| 결제 성공률 baseline -2%p | "리스크가 큰 것 같다" |
| 사용자 이탈률 baseline +10% | "트래픽이 좀 이상한듯" |

원칙: **숫자 + 지표 이름 없으면 신호가 아니다.**

## 작업 절차

1. **변경의 *영향 영역* 식별** — 어떤 서비스·기능·사용자 그룹?
2. **그 영역의 *측정 가능 지표* 확인** — 기존 모니터링/대시보드에 뭐가 있나
3. **baseline 측정** — 변경 *전* 의 평소 값. 임계값은 baseline 대비 정의
4. **3~5개 신호 + 임계값 정의**
5. **각 신호의 *대응 액션* 명시** — 임계값 닿으면 정확히 뭘 함
6. ***결정자 + 알림* 경로** — 누가 롤백 결정? PagerDuty? Slack 채널?
7. **측정 인프라 없는 영역이면 "Phase 0: 측정 추가" 가 변경 전제 조건** 으로 명시

## 출력 템플릿

```markdown
## 롤백 계획 — <변경 이름>

### 영향 영역
<서비스 · 사용자 그룹 · 의존 시스템>

### Baseline (변경 전)
- <지표 1>: <값>
- <지표 2>: <값>

### 신호 3~5개

#### 신호 ①: <짧은 이름>
- 임계값: <지표> > <값> (baseline +X%)
- 측정 위치: <대시보드 / 로그 / 알림 시스템>
- 대응: <flag off / phase 보류 / 옛 구현 복원>
- 결정자: <누가> · 알림: <어디로>

#### 신호 ②: …
#### 신호 ③: …

### 측정 인프라 갭
- <측정 안 되는 신호가 있으면 Phase 0 으로 명시>
```

## 안티 패턴

- ❌ 측정 안 되는 신호 ("느낌이 안 좋다", "팀이 불안")
- ❌ 신호만 있고 *대응 액션* 없음 — 신호 보고 뭘 할지 모름
- ❌ 결정자 모호 — "팀이 결정" 은 결정자 아님. *한 명* 이름 또는 *명확한 룰* 필요
- ❌ baseline 없이 임계값 정의 — 비교 기준 없음
- ❌ 신호 1개만 — 한 지표만 보면 사각지대
- ❌ 신호 7개+ — 너무 많아 운영 중 추적 불가
