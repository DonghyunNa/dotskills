# dev-breakdown-tasks

## 무엇을 하는가

큰 업무 흐름을 받아서 **그 자리에서 손에 잡히는 작은 작업들로 분해**한다. 결과물은 단순 리스트가 아니라, 다음 4가지가 다 박힌 실행 계획이다.

1. **단계(Phase)** — 큰 흐름을 시간 순/의존성 순으로 묶음
2. **원자 작업(Atomic task)** — 한 번 앉아서 끝낼 수 있는 단위 (체크리스트 형태)
3. **완료 기준(Done when)** — 각 작업이 끝났음을 *관찰*할 수 있는 신호
4. **가정·미해결 질문(Open)** — 시작 전에 확인해야 할 것들

## 언제 호출되나

- 사용자가 "이거 어떻게 시작하지", "업무 쪼개줘", "task breakdown", "WBS 만들어줘" 같은 표현을 쓸 때
- 큰 프로젝트 킥오프, 분기 계획, 마이그레이션 계획, 기능 출시 계획 등 *시작 직전*의 흐릿한 상태
- Claude가 사용자 메시지에서 "할 일이 큰 덩어리로만 묘사되고 있다"고 판단할 때

## 언제 호출하지 않나

- 이미 1~2시간 단위로 잘게 쪼개진 todo 리스트가 있을 때 → 그대로 실행
- 단일 액션 (예: "이 함수 이름 바꿔줘") → 그냥 한다
- 코드 레벨 리팩토링 분해 → 별도 리팩토링 스킬 영역
- 요구사항 자체가 모호할 때 → 먼저 `deep-interview` 로 정리한 다음 본 스킬 호출

## 작업 절차

### 1. 입력 정규화 (1~2분)

사용자가 말한 업무 흐름을 한 단락으로 정리해서 *되돌려 보여준다*. "내가 이해한 게 맞나" 합의 단계. 동의가 떨어지기 전엔 다음으로 안 넘어간다.

### 2. 결과물 정의

"이 업무가 *완료됐다*는 걸 어떻게 알 수 있나?" — 최종 산출물 1~3개를 명시한다. 분해의 기준점이 된다.

### 3. 단계(Phase) 식별

시간 순서 또는 의존성 순서로 3~7개 phase를 뽑는다. 각 phase 이름은 *동사로 시작하는 짧은 구* (예: "데이터 준비", "초기 프로토타입", "사용자 테스트").

너무 많으면(>7) phase 자체를 한 단계 더 묶고, 너무 적으면(≤2) 분해를 더 진행한다.

### 4. 원자 작업으로 쪼개기

각 phase 안에서 작업을 뽑을 때 **모든 작업이 다음 3가지를 통과**해야 한다.

| 체크 | 기준 |
|---|---|
| **Actionable** | 동사로 시작한다 ("X를 만든다", "Y를 실행한다"). "X에 대해 생각한다"는 ✗ |
| **Small** | 한 번 앉아서 (대략 2시간 이내) 끝낼 수 있다. 더 크면 더 쪼갠다 |
| **Verifiable** | 끝났는지 *외부에서 관찰*할 수 있다 (파일 존재, 테스트 통과, PR 머지, 발표 완료 등) |

### 5. 의존성·가정 표시

- 작업 A가 B의 결과를 필요로 하면 `→ depends on #B` 로 표기.
- 시작 전에 확인되어야 할 가정·미정 사항은 끝의 `## Open` 섹션에 모은다. *지금 알 수 없는 것*을 명시하는 게 중요. 모른다고 작업 안에 숨기지 않는다.

## 출력 템플릿

분해 결과는 항상 아래 마크다운 구조로 낸다.

```markdown
## 목표
<한 단락 — 이 업무가 끝나면 무엇이 존재/달성되는가>

## 산출물
- <observable artifact 1>
- <observable artifact 2>

## Phase 1: <동사로 시작>
- [ ] **#1.1** <atomic task> _(done when: <observable signal>)_
- [ ] **#1.2** <atomic task> _(done when: <…>)_ → depends on #1.1

## Phase 2: <…>
- [ ] **#2.1** <…>
…

## Open
- <가정 / 확인 필요한 것 / 결정 보류 사항>
```

번호 매기기는 `#phase.task` (예: #2.3). 의존성 표기 시 이 번호를 쓴다.

## 예시

**입력**: "치즈버튼 백오피스에 결제 환불 기능을 추가하려고 해. 어디서부터 손대야 할지 모르겠어."

**출력**:

```markdown
## 목표
백오피스 운영자가 결제 1건을 조회해서 환불 요청을 실행할 수 있게 한다.
환불은 PG사를 호출해 성공 시 DB 상태가 `refunded`로 바뀐다.

## 산출물
- 결제 상세 화면의 [환불] 버튼 + 사유 입력 모달
- `POST /admin/payments/:id/refund` API (PG 호출 + 상태 전이)
- 운영자 권한 가드 + 환불 이력 로그
- 통합 테스트 1건 (환불 성공 → 상태 `refunded` 확인)

## Phase 1: 도메인 정리
- [ ] **#1.1** 환불 정책 문서 1쪽 작성 (부분환불 허용? 기한? 권한?) _(done when: 결제 PO 승인 코멘트)_
- [ ] **#1.2** 현재 결제 상태머신에 `refunded` 전이 추가 가능 여부 코드로 확인 _(done when: payment_status.go 변경 디자인 메모)_

## Phase 2: API 백엔드
- [ ] **#2.1** `POST /admin/payments/:id/refund` 엔드포인트 스켈레톤 + 권한 미들웨어 _(done when: 단위 테스트로 401/403 통과)_ → depends on #1.1
- [ ] **#2.2** PG 환불 호출 모듈 작성 + 실패 케이스 mapping _(done when: PG sandbox에서 1건 환불 성공)_
- [ ] **#2.3** DB 상태 전이 + 환불 이력 row 기록 _(done when: SQL 마이그레이션 머지 + 통합 테스트 1건 그린)_ → depends on #1.2, #2.2

## Phase 3: 백오피스 UI
- [ ] **#3.1** 결제 상세 화면에 [환불] 버튼 + 사유 모달 컴포넌트 _(done when: 스토리북 추가)_
- [ ] **#3.2** API 연결 + 성공/실패 토스트 _(done when: staging에서 1건 환불 끝까지 흘려봄)_ → depends on #2.3, #3.1

## Phase 4: 출시 준비
- [ ] **#4.1** 운영자용 매뉴얼 1쪽 (어떻게 환불, 사후 확인 어디서) _(done when: Notion 페이지 공유 링크)_
- [ ] **#4.2** Feature flag 뒤에 두고 운영 1명에게만 노출 _(done when: prod에서 flag on/off 확인)_ → depends on #3.2

## Open
- 부분 환불 지원 범위 (전체만? 금액 지정?) — PO 응답 대기
- PG 환불 timeout이 길 때 UI 처리 (비동기 큐로 뺄지 결정 필요)
- 환불 권한을 기존 admin 권한과 분리할지 (#1.1에서 같이 정함)
```

## 안티 패턴 (피해야 할 것)

- ❌ "X에 대해 생각한다", "X를 검토한다" — 행동이 아니고 끝났는지 모름
- ❌ Phase 안에 작업이 1개뿐 — phase 분리 의미 없음. 다른 phase에 합치거나 더 쪼개기
- ❌ 작업 하나에 "그리고", "또" 가 들어감 — 사실 2개 작업
- ❌ 의존성이 사슬처럼 줄줄이 — 병렬화 가능한지 다시 본다
- ❌ Open 섹션이 비어 있음 — 정말 가정·미정이 없는 큰 업무는 드물다. 한 번 더 생각

## 다른 스킬과의 관계

- [[deep-interview]] — 요구사항 자체가 흐릿할 때 *먼저* 호출. 본 스킬은 "할 일은 명확한데 어디서 시작할지"가 막힐 때.
- TaskCreate 도구 — 분해 결과를 그대로 Claude Code의 task list로 등록할 때 유용.
