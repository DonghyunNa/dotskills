# Output template

작업 절차의 6개 산출물을 담는 단일 마크다운 구조. 사용자에게 제출할 *최종 출력* 형식.

```markdown
# 레거시 현대화 전략: <대상 모듈/서비스>

## 1. 인테이크 요약
- **범위**: <합의된 모듈/서비스 경계>
- **동기**: <왜 지금 — incident / 성능 / 채용 / 기능 막힘 / 컴플라이언스 등>
- **제약**: <시간 / 인력 / downtime 허용도 / 외부 의존>
- **성공 정의**: <6개월~1년 뒤 관찰 가능한 신호>
- **리스크 허용도**: <한 번에 큰 변화 vs 점진적, prod 영향 범위>

## 2. 진단
- 변경 hotspot: <상위 5~10 파일>
- 테스트 커버리지: <% 또는 영역별 부재>
- 결합도: <순환 / fan-in 페어>
- 외부 통합: <DB·API·큐·파일시스템>
- 알려진 이슈 영역: <TODO 집중, hotfix 다발>
- 빌드·배포 사이클: <변경→prod 시간, 테스트 실행 시간>
- 도메인 경계 후보: <응집도 높은 그룹>
- 위험 신호: <종합 평가 한 단락>

## 3. 후보 전략 (3~5개)

### 옵션 A: <카탈로그 패턴 이름>
- **핵심**: <한 단락>
- **이 사례 적합도**: <왜 이게 후보인지 1~2문장>
- **예상 비용/시간**: <대략>

### 옵션 B: <…>
### 옵션 C: <…>

## 4. 위험-효과 매트릭스

| 옵션 | 효과 | 시간 | 리스크 | 의존 | 되돌리기 |
|---|---|---|---|---|---|
| A | 높/중/낮 | 1주/1달/분기/반기+ | 높/중/낮 | <필요한 외부 자원> | 저/중/고 |
| B | … | … | … | … | … |
| C | … | … | … | … | … |

## 5. 추천: <옵션 X>

근거:
- <매트릭스 축 기반 1~2 포인트>
- <§1 제약과의 정합성>
- <카탈로그의 원전 적용 근거가 있다면>

대안 옵션이 더 적합해지는 *조건*:
- <어떤 정보가 더 들어오면 다른 옵션이 우세인지>

## 6. 실행 계획

**Phase 1은 안전망**.

- [ ] **#1.1** <characterization test 작성 또는 모니터링 추가> _(done when: <관찰 가능한 신호>)_
- [ ] **#1.2** <…> _(done when: <…>)_ → depends on #1.1

### Phase 2: <전략 본 작업의 첫 단계>
- [ ] **#2.1** <…> _(done when: <…>)_ → depends on #1.x
- …

### Phase 3+: <전략에 따른 후속 단계>
…

## 7. 롤백 신호 — *측정 가능* 형태로 3~5개

- 에러율이 baseline 대비 X% 초과 (지표: <어떤 지표>)
- 응답 시간 P95 가 Y ms 초과 (엔드포인트: <어디>)
- 같은 종류 incident 가 N일 안에 K건
- 팀 속도 (merged PR/주) 가 기대치의 Z% 미만으로 M주 지속
- <이 사례 고유의 측정 가능 신호>

각 신호마다 *대응 액션* 도 같이:
- 신호 ① 발생 시 → flag off, 옛 구현 복원
- 신호 ② 발생 시 → 다음 Phase 진입 보류, 원인 분석 후 §3 옵션 재평가

## Open — 가정 / 확인 필요

- <인테이크에서 미해결인 가정>
- <진단으로 명확해지지 않은 부분>
- <외부 팀/이해관계자 확인 대기 항목>
```

## 작성 시 주의

- 데이터 없는 추측은 *Open* 으로 — 본문에 추측 섞지 말 것
- 추천 근거에 카탈로그 패턴의 원전(Fowler, Feathers 등)이 적용 가능하면 짧게 인용
- "느낌이 안 좋다" 류 비정량 표현은 §7에서 *측정 가능 신호로 번역* 하거나 빼기
- 매트릭스의 같은 옵션은 같은 행에서 일관 — 효과 "높" 인데 리스크 "낮" 같은 비현실적 조합 자주 등장 → 사용자와 확인
