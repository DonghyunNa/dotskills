# dev-modernize-legacy

## 무엇을 하는가

레거시 모듈/서비스/리포지토리를 받아 **현실적인 현대화 전략**을 만든다. 추측 기반의 "다시 짜자" 가 아니라 다음 6개 산출물이 다 박힌 의사결정 가능한 문서:

1. **진단 리포트** — 객관적 지표로 본 현재 상태
2. **후보 전략 3~5개** — 카탈로그에서 사례에 맞게 선별
3. **위험-효과 매트릭스** — 같은 축으로 후보 비교
4. **추천 + 근거**
5. **단계별 실행 계획** — Phase 1은 *거의 항상* 안전망
6. **롤백 신호** — "여기서 멈춰라" 의 객관적 측정 가능 기준

## 언제 호출되나

- 큰 모듈/서비스를 *조금씩* 바꿔야 할 때 ("저 부분 손대고 싶은데 무서워")
- 의사결정자에게 옵션을 제시해야 할 때 (rewrite vs refactor vs leave-alone)
- 기술부채 우선순위 회의 자료 준비
- "여기 strangler fig 어떻게 적용?" 같은 구체 패턴 자문

## 언제 호출하지 않나

- 한두 시간이면 끝날 국소 리팩토링 — 그냥 한다
- 그린필드 새 프로젝트 — 다른 스킬 (아키텍처 설계)
- 단일 함수 이름 변경·타입 보강 — 그냥 한다
- 이미 합의된 마이그레이션 실행 단계로 들어왔을 때 — [[task-breakdown]] 만 호출

## 작업 절차

### 1. 인테이크 — `deep-interview` 호출

5가지가 명확해질 때까지 질문. 흐릿하면 이 단계에서 멈추고 [[deep-interview]] 로 위임.

- **대상 범위** — 어떤 모듈/서비스? 경계가 어디?
- **동기** — 왜 *지금*? (incident? 성능? 채용? 새 기능 막힘? 컴플라이언스?)
- **제약** — 시간, 인력, 운영 중인 시스템인지, downtime 허용도, 외부 의존
- **성공 정의** — 6개월/1년 뒤 무엇이 *관찰* 가능해야 성공?
- **리스크 허용도** — 한 번에 큰 변화 vs 점진적, prod 영향 어디까지 허용?

### 2. 진단 — `Explore` 서브에이전트 병렬

대상 코드를 5~7개 축으로 *동시* 스캔. 한 번에 1개 씩 직렬로 가지 말고 fan-out:

| 축 | 무엇을 본다 | 어떻게 |
|---|---|---|
| 변경 빈도 | hotspot 식별 | `git log --since="6 months ago" --pretty=format: --name-only \| sort \| uniq -c \| sort -rn \| head -30` |
| 테스트 커버리지 | 안전망 없는 영역 | 커버리지 리포트, 또는 테스트 파일/소스 파일 비율 |
| 결합도 | 변경 충격 반경 | import 그래프, 순환 의존, fan-in/fan-out |
| 외부 통합 지점 | 깨지면 큰 곳 | DB / 외부 API / 메시지큐 / 파일시스템 호출 위치 |
| 알려진 이슈 영역 | 도메인 지식 발굴 | TODO / FIXME / HACK 주석, `git log --grep="hotfix\\|incident"` |
| 빌드·배포 사이클 | 피드백 루프 길이 | 변경에서 prod까지 시간, 테스트 실행 시간 |
| 도메인 경계 | bounded context 후보 | 응집도 높은 디렉토리/모듈 그룹, 공통 도메인 용어 |

각 결과를 *진단 리포트* 한 페이지로 정리. 데이터 없는 추측은 넣지 말 것.

### 3. 옵션 도출 — 카탈로그 큐레이션

아래 **전략 카탈로그**에서 이 사례에 *적용 가능한 3~5개*만 골라 후보로. 각 후보마다 "이 사례에 왜 적합/부적합" 1~2문장.

7개 전부 나열하는 건 가치 없음 — *큐레이션 자체*가 이 스킬의 부가가치.

### 4. 평가 — 위험-효과 매트릭스

모든 후보를 같은 5축으로 평가. 표 한 장에 들어가야 함.

| 축 | 측정 |
|---|---|
| **효과** | 6개월 후 §1의 성공 정의 충족도 (높/중/낮) |
| **시간** | 1주 / 1달 / 분기 / 반기+ |
| **리스크** | prod 장애·데이터 손상 가능성 (높/중/낮) |
| **의존** | 외부 팀·툴·예산 필요 여부 |
| **되돌리기** | 망쳤을 때 롤백 비용 (저/중/고) |

### 5. 선택 + 분해 — `task-breakdown` 호출

추천 전략을 채택한 다음 [[task-breakdown]] 으로 Phase/Atomic task/Done-when 구조로 분해.

**Phase 1은 거의 항상 "안전망 구축"** (아래 안전망 우선 원칙 참고).

### 6. 롤백 신호

"이 신호가 보이면 멈추거나 되돌린다" 를 *객관적 측정 가능*한 형태로 3~5개:

- 에러율 X% 증가 (어떤 지표 기준)
- 응답 시간 P95 Y ms 초과 (어떤 엔드포인트)
- 같은 종류 incident가 N일 안에 K건
- 팀 속도(merged PR/주)가 기대치 대비 Z% 미달이 M주 지속

신호 *없이* 들어가지 말 것 — "느낌이 안 좋다" 는 롤백 트리거가 아니다.

## 전략 카탈로그

### Strangler Fig (Fowler)
새 구현을 옛 구현 옆에 두고 트래픽/호출을 점진 이전. 옛것은 마지막에 제거.
- ✅ 외부 인터페이스(API/UI) 유지하면서 내부 교체
- ✅ 다운타임 불가능한 시스템
- ✗ 옛-새 코드가 같은 상태를 동시 변경해야 할 때 (동기화 지옥)

### Branch by Abstraction
교체 대상을 인터페이스/추상화 뒤로 숨김 → 옛·새 구현 둘 다 같은 인터페이스 만족. flag로 전환.
- ✅ 내부 라이브러리/모듈 교체
- ✅ 옛것 *돌리면서* 새것 개발해야 할 때
- ✗ 외부 노출 API 자체를 바꿔야 할 때

### Characterization Tests (Feathers)
손대기 전에 *현재 동작*을 그대로 캡처하는 테스트부터 작성. "이게 옳은가" 묻지 말고 "지금 뭘 하나"만 기록.
- ✅ 거의 항상 Phase 1에 들어감
- ✅ 의도 파악하기 어려운 비즈니스 로직

### Mikado Method
"이걸 바꾸려면 무엇을 먼저?"를 반복해 의존성 그래프 역추적. 잎부터 작업.
- ✅ "어디서부터 시작?"이 막힐 때
- ✅ 변경이 줄줄이 다른 곳을 깨는 영역

### Golden Master / Parallel Run
신·구 시스템 동시 가동 → 같은 입력에 다른 출력 나오면 알람. 신뢰가 쌓이면 옛것 제거.
- ✅ 비즈니스 로직 (계산·가격·매칭) 재작성
- ✅ 결정성 있는 입출력
- ✗ 비결정적 동작 (외부 시간/난수/외부 API 결과 의존)

### 부분 재작성 + 단계적 마이그레이션
모듈 단위로 새로 짜고 하나씩 흡수. 큰 재작성을 작은 재작성 N개로 쪼갬.
- ✅ 도메인 경계가 명확할 때 (bounded context)
- ✗ 강결합으로 경계가 흐릴 때 → Mikado 먼저

### Big Bang Rewrite
처음부터 다시. *거의 항상 비추천*, 가끔 답.
- ✅ 옛 코드 유지 비용 > 새로 짜는 비용 (드뭄)
- ✅ 옛 스택이 곧 죽음 (언어/HW EOL, 보안 패치 종료)
- ✗ 대부분 — Joel Spolsky's "Things You Should Never Do, Part I" 참고

### Leave Alone
의외로 정답. 안 바뀌고 잘 돌면 그대로 둬라.
- ✅ 변경 빈도 낮고 incident 없는 영역
- ✅ 다른 우선순위가 더 큰 ROI

## 안전망 우선 원칙

§5 Phase 1은 **거의 항상**:

- 테스트 없으면 → Characterization tests + 핵심 시나리오 통합 테스트
- 모니터링 없으면 → 핵심 지표(에러율·지연·사용량) 계측 + 알림
- 롤백 경로 없으면 → feature flag + DB 마이그레이션 reverse 가능성 점검

> "안전망 없이 진입 = 그 다음 사고 보고서를 미리 쓰는 것"

## 출력 템플릿

```markdown
# 레거시 현대화 전략: <대상 모듈/서비스>

## 1. 진단
- 대상 범위: <한 단락>
- 변경 hotspot: <상위 5~10 파일>
- 테스트 커버리지: <%, 또는 영역별 부재 표시>
- 결합도: <순환 의존 / 결합도 높은 페어>
- 외부 통합: <DB/API/큐 목록>
- 알려진 이슈 영역: <TODO·HACK·incident 로그 키워드>
- 빌드·배포 사이클: <변경→prod 시간>
- 도메인 경계 후보: <응집도 높은 그룹>
- 위험 신호: <전반적 평가>

## 2. 후보 전략

### 옵션 A: <카탈로그 패턴 이름>
- 핵심: <1~2 문장>
- 이 사례 적합도: <왜 이게 후보인지>
- 예상 비용/시간: <대략>

### 옵션 B: …
### 옵션 C: …

## 3. 위험-효과 매트릭스

| 옵션 | 효과 | 시간 | 리스크 | 의존 | 되돌리기 |
|---|---|---|---|---|---|
| A | 높 | 분기 | 중 | 없음 | 중 |
| B | 중 | 1달 | 낮 | 데이터팀 | 저 |
| C | 높 | 반기+ | 높 | 보안팀 | 고 |

## 4. 추천: <옵션 X>

근거:
- <축 기반 1~2 포인트>
- <제약과의 정합성>

## 5. 실행 계획

[task-breakdown 호출 결과를 그대로 임베드 — Phase / Done when / Open]

Phase 1은 안전망:
- [ ] **#1.1** <characterization test 작성> _(done when: ...)_
- [ ] **#1.2** <핵심 지표 모니터링 추가> _(done when: ...)_
- …

## 6. 롤백 신호

- <측정 가능한 신호 1, 임계값 포함>
- <측정 가능한 신호 2>
- …

## Open

- <인테이크에서 미해결 가정>
- <진단으로 명확해지지 않은 부분>
```

## 안티 패턴

- ❌ §1 인테이크 건너뛰기 — "왜?"를 모르면 옵션 평가 불가
- ❌ §2 진단 데이터 없이 옵션부터 던지기 — 추천 신뢰도 0
- ❌ Phase 1이 안전망이 아닌 것으로 시작 — 사고 보고서 예약
- ❌ Big Bang을 default 추천 — 거의 항상 틀림. 추천하려면 *명시적* 근거 필요
- ❌ "현대화" 가 사실 "내 취향 스택으로 다시 짜기" 인 경우 — §1에서 동기 진위 검증
- ❌ 후보 7개 다 나열 — 큐레이션 안 한 것. 3~5개로 좁힐 것
- ❌ 롤백 신호가 "느낌" — 측정 가능한 임계값 없으면 신호가 아님

## 다른 스킬과의 관계

- [[deep-interview]] — §1 인테이크. 동기/제약/성공 정의가 흐릿하면 *반드시* 먼저.
- [[task-breakdown]] — §5 실행 계획 분해. 출력을 그대로 임베드.
- `Explore` 서브에이전트 — §2 진단. 5~7 축에 대해 *병렬* 호출 권장 (직렬 X).
- `Plan` 서브에이전트 — §3 옵션 도출 시 아키텍처 대안 검토에 활용 가능.
