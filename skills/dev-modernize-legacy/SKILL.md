# dev-modernize-legacy

## 무엇을 하는가

레거시 모듈/서비스/리포지토리를 받아 **6개 산출물이 박힌 의사결정 가능한 전략 문서** 를 만든다.

이 스킬은 *오케스트레이터*. 인테이크·진단·옵션 비교·계획 분해·롤백 신호는 같은 repo 의 *전용 sub-skill* 에 위임하고, 본 스킬은 **레거시 도메인 지식 = 전략 카탈로그 큐레이션 + 단계 조립** 만 담당.

## 언제 호출되나

- 큰 모듈/서비스를 *조금씩* 바꿔야 할 때 ("저 부분 손대고 싶은데 무서워")
- 의사결정자에게 옵션 제시 (rewrite vs refactor vs leave-alone)
- 기술부채 우선순위 회의 자료 준비
- 구체 패턴 자문 ("여기 strangler fig 어떻게 적용?")

## 언제 호출하지 않나

- 한두 시간이면 끝날 국소 리팩토링
- 그린필드 새 프로젝트
- 단일 함수 이름 변경·타입 보강
- 이미 합의된 마이그레이션의 실행 단계 — `dev-breakdown-tasks` 직접 호출

## 작업 절차 — 6단계 오케스트레이션

### §1. 인테이크 → [[dev-clarify-requirements]]

5축(범위·동기·제약·성공 정의·리스크 허용도) 모두 그대로 위임. 레거시 맥락에서 자주 등장하는 답:

- **동기**: incident · 성능 · 채용 · 기능 막힘 · 컴플라이언스
- **제약**: downtime 허용도 · 외부 팀 의존
- **성공 정의**: 6개월~1년 시점의 *관찰 가능* 신호

### §2. 진단 → [[dev-diagnose-repo]]

7축(hotspot · 커버리지 · 결합도 · 외부 통합 · 알려진 이슈 · 빌드 사이클 · 도메인 경계) 한 페이지 리포트. 그대로 위임.

### §3. 옵션 도출 — 본 스킬의 도메인 지식

`references/strategy-catalog.md` 의 8개 패턴 중 *이 사례에 적용 가능한 3~5개* 만 큐레이션. 카탈로그 끝의 "큐레이션 가이드" 가 기준 제공.

8개 전부 나열은 큐레이션 안 한 것.

### §4. 평가 → [[dev-compare-options]]

5축(효과·시간·리스크·의존·되돌리기) 매트릭스. 위임. 축 정의는 sub-skill 기본 그대로 — 레거시 맥락만 살짝 좁혀:

- **효과**: §1 성공 정의 충족도
- **리스크**: prod 장애·데이터 손상
- **되돌리기**: 망쳤을 때 롤백 비용

### §5. 분해 → [[dev-breakdown-tasks]]

선택된 전략을 Phase / Atomic task / Done-when 으로. **Phase 1은 거의 항상 안전망**:

- 테스트 없으면 → characterization tests + 핵심 시나리오 통합 테스트
- 모니터링 없으면 → 핵심 지표(에러율·지연·사용량) 계측 + 알림
- 롤백 경로 없으면 → feature flag + DB 마이그레이션 reverse 가능성

> 안전망 없이 진입 = 그 다음 사고 보고서를 미리 쓰는 것.

### §6. 롤백 신호 → [[dev-plan-rollback]]

객관적 임계값 3~5개 + 대응 액션 + 결정자/알림 경로. 위임.

## 출력 형식

6개 산출물을 단일 마크다운으로 조립:

→ `references/plan-template.md`

각 섹션은 대응 sub-skill 의 출력을 그대로 임베드.

## 안티 패턴 (본 스킬 영역)

- ❌ §3 카탈로그 8개 전부 나열 — 큐레이션 안 한 것
- ❌ Big Bang 을 default 추천 — 명시적·정량 근거 없이는 거의 항상 틀림
- ❌ "현대화" 가 사실 "내 취향 스택으로 다시 짜기" — §1 동기 진위 검증
- ❌ Phase 1이 안전망이 아닌 것 — §5 sub-skill 이 안전망 검증
- ❌ sub-skill 출력을 사용자에게 *그대로* 재출력 — 통합 문서로 조립해야 함

각 단계 내부의 안티패턴은 해당 sub-skill 에 위임.
