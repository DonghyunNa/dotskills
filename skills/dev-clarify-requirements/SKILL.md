# dev-clarify-requirements

## 무엇을 하는가

흐릿한 개발 작업 묘사를 받아 **시작에 충분한 5축 요구사항 문서** 로 정리한다. 답이 있는 축은 그대로 옮기고, 없는 축은 *추측 없이* 사용자에게 묻거나 Open 으로 남긴다.

## 5축

| 축 | 묻는 것 | 흐릿한 예 → 명확한 예 |
|---|---|---|
| **범위** | 무엇을 / 어디까지? 경계는? | "결제 개선" → "결제 상세 화면 + 환불 API + 운영자 권한 가드" |
| **동기** | 왜 *지금* 하나? | "오래돼서" → "지난 분기 incident 3건이 모두 이 모듈" |
| **제약** | 시간 · 인력 · 예산 · 품질 기준 · 외부 의존 | "빨리" → "분기 안에 1.5 FTE, downtime 30분 OK, 보안팀 승인 필요" |
| **성공 정의** | 끝났을 때 *관찰 가능* 한 신호 | "잘 굴러간다" → "환불 처리 시간 P95 < 5초, 환불 실패율 < 0.5%" |
| **리스크 허용도** | 망쳤을 때 어디까지 OK? | "리스크 최소" → "prod 일시 장애 1시간까지 OK, 결제 누수는 NO" |

## 작업 절차

1. **사용자 입력에서 5축 중 *이미 답이 있는 것* 추출**
2. **없거나 흐릿한 것만 질문** — 한 번에 5개 다 묻지 말고, 가장 중요한 1~2개부터
3. **답변을 구조화된 문서로 정리**
4. **미해결 항목은 `Open` 섹션에 그대로 남김** — 추측해서 채우지 않음

## 출력 템플릿

```markdown
## 요구사항

- **범위**: <구체 경계>
- **동기**: <왜 지금>
- **제약**: <시간/인력/품질/의존>
- **성공 정의**: <측정 가능한 신호>
- **리스크 허용도**: <허용 범위>

## Open

- <답이 안 나온 축, 또는 더 좁혀야 할 부분>
- <확인 대기 중인 외부 응답>
```

## 안티 패턴

- ❌ 이미 답이 있는 축까지 묻기 — 사용자 시간 낭비
- ❌ 답이 흐릿한데 *추측* 으로 채우기 → 잘못된 전제로 진행
- ❌ "글로벌하게 좋은 코드" 같은 *측정 불가* 성공 정의 허용
- ❌ 5축을 한꺼번에 다 묻기 — 1~2개씩 진행해 사용자 피로 분산
- ❌ Open 섹션이 비어 있음 — 정말 모든 게 명확한 작업은 드뭄
